# Vue3 Composable 设计专题练习

## 第 1 题：商品数量选择器 `useQuantity`

### 题目背景

购物车里的每个商品都有数量选择器：可以增加、减少、手动输入以及恢复默认数量。不同商品遵守相同规则，但数量互不影响。请将这些规则封装为一个可在组件中使用的 composable。

### 已有代码 / 初始条件

```ts
interface QuantityOptions {
  initial: number
  min: number
  max: number
  step?: number
}

export function useQuantity(options: QuantityOptions) {
  // TODO：设计状态、公开操作和返回值类型。
}
```

调用方需要展示当前数量、是否还能增加、是否还能减少，以及是否偏离初始数量。请自行设计这些信息的返回形式。

本题约定配置在调用时确定，之后不变；`initial`、`min`、`max` 都是安全整数，且 `min <= initial <= max`。`step` 是正整数，默认值为 `1`。无需处理非法配置。

### 核心需求

1. 提供增加、减少、设置数量、重置四种操作。增加或减少跨越边界时，停在边界值。
2. 设置数量接受 `number`：有限小数先向零取整，再限制在区间内；`NaN` 和无穷值不改变当前数量。
3. 重置回本次调用的 `initial`，不是回到下限。
4. 当前数量变化后，所有展示信息都应保持一致。
5. 同一个组件调用两次、两个组件分别调用时，每次调用都拥有独立数量。

### 设计约束

- 使用 TypeScript，为参数、公开操作和返回值提供可理解的类型。
- 调用方只能通过公开操作修改数量，不能通过返回值绕过范围约束。
- 返回结果可以解构后用于模板，并保持响应性。
- 不使用 Pinia，不操作 DOM，不加入存储或请求功能。

### 思考问题

1. 哪些信息需要保存，哪些信息只取决于其他信息？额外保存它们会增加什么维护成本？
2. 对当前数量、按钮可用状态和重置操作，你如何判断是否需要 `computed`、`watch`、`watchEffect`，或者都不需要？
3. 返回一个响应式对象和返回一个包含响应式成员的普通对象，对调用方解构有什么影响？
4. 如何让类型约束与运行时行为共同维护“只能通过操作修改数量”的约定？

### 验收场景

- A 使用 `{ initial: 2, min: 1, max: 5, step: 2 }`：连续增加得到 `4`、`5`、`5`；此时不能继续增加，但可以减少。
- A 设置 `3.9` 后数量为 `3`；设置 `-2` 后为 `1`；设置 `NaN` 后仍为 `1`。
- A 从 `1` 重置后为 `2`，偏离初始数量的标记随之恢复。
- B 使用相同配置，A 的所有操作都不改变 B 的数量。
- 调用方解构返回成员后，执行增加操作，模板中的数量和按钮状态仍正确更新。
- 尝试直接为公开数量赋值，不能成为绕过公开操作的有效修改路径。

## 第 2 题：批量选择中的独立状态与共享状态 `useSelection`

### 题目背景

后台页面有两个工作区。每个工作区都有一个表格和一个批量操作工具栏：表格勾选行后，工具栏显示已选数量，也可以清空选择。同一工作区需要共享选择状态，不同工作区需要隔离。

另有一个独立的选择弹窗，它只需要自己的临时选择状态。

### 已有代码 / 初始条件

```ts
type RowId = string

// 这是待设计的公开入口，参数与返回类型由你补充。
export function useSelection(/* TODO */) {
  // TODO
}
```

页面关系如下：

```text
Page
├─ Workspace A
│  ├─ Table A
│  └─ Toolbar A
├─ Workspace B
│  ├─ Table B
│  └─ Toolbar B
└─ SelectionDialog
```

请另外比较下面两段候选代码的行为。它们仅供分析，不代表本题的最终 API：

```ts
// 候选一
const selectedIds = ref<string[]>([])

export function useSelection() {
  return { selectedIds }
}
```

```ts
// 候选二
export function useSelection() {
  const selectedIds = ref<string[]>([])
  return { selectedIds }
}
```

### 核心需求

1. 提供切换某个 ID 的选中状态、判断是否选中、清空选择的能力，公开已选 ID 和数量。
2. 同一 ID 不能重复出现；工具栏无需知道表格内部实现即可操作当前工作区的选择。
3. Table A 与 Toolbar A 共享选择；Table B 与 Toolbar B 共享另一份选择；A、B 互不影响。
4. 弹窗每次重新挂载都从空选择开始，不读取任何工作区的选择。
5. 只卸载 Toolbar A 再挂载，A 的选择仍在；整个 Workspace A 卸载后重新创建，A 从空选择开始。
6. 给出最小的父组件、表格和工具栏接入示例，让状态的创建者、使用者和销毁边界可以从代码中看出来。

### 设计约束

- 不使用 Pinia、全局事件总线或浏览器存储。
- 不通过复制两份状态再互相同步来实现同一工作区的共享。
- 不硬编码工作区 A、B；同一页面可以再创建一个独立工作区。
- 调用方不能通过修改公开数组绕过选择操作；共享方式及上下文缺失时的行为由你设计并说明。
- 仅考虑客户端页面，无需实现服务端渲染支持。

### 思考问题

1. 两段候选代码分别在什么范围内共享状态？哪一段能直接满足整个页面的需求，或者都不能？
2. 表格和工具栏都需要状态，但谁应该决定这份状态何时创建、何时结束？
3. “一个工作区共享”和“整个应用共享”在 API 上如何区分，才能让调用方不容易误用？
4. 同一种选择逻辑既用于独立弹窗又用于共享工作区时，哪些代码值得复用，哪些职责应留给组件？

### 验收场景

- Table A 依次选中 `u1`、`u2`，Toolbar A 显示 `2`，Toolbar B 仍显示 `0`。
- Toolbar A 清空后，Table A 的勾选状态一起清空；B 已有的选择保持不变。
- 同一个 ID 连续切换两次，恢复到切换前的选中状态，不产生重复 ID。
- 卸载并重新挂载 Toolbar A，仍能读取 A 已有的选择。
- 卸载整个 Workspace A 后再创建，新的 A 为空，仍挂载的 B 保留其选择。
- 打开弹窗、选择 `u3`、销毁弹窗、重新打开，新弹窗为空。

## 第 3 题：可切换目标的事件监听 `useEventListener`

### 题目背景

一个可折叠面板需要记录用户点击。面板可能尚未挂载，也可能被条件渲染替换；设置里还有一个开关，可以临时关闭记录。请设计一个负责监听和释放资源的 composable，让组件只处理点击后的业务行为。

### 已有代码 / 初始条件

```vue
<script setup lang="ts">
import { ref } from 'vue'

const panel = ref<HTMLElement | null>(null)
const enabled = ref(true)
const clickCount = ref(0)

function handleClick(event: MouseEvent) {
  clickCount.value += 1
}

// TODO：调用你设计的 useEventListener，将 panel、enabled 和 handleClick 接入。
</script>

<template>
  <section ref="panel">点击区域</section>
  <p>已记录 {{ clickCount }} 次点击</p>
</template>
```

本题只要求支持 `HTMLElement` 的 `click` 事件，事件名称和处理函数在调用后不变。目标可以是普通元素、保存元素的 ref、返回元素的 computed 或 getter；目标暂不存在时为 `null`。启用状态也应支持普通布尔值、ref、computed 或 getter，省略时默认启用。

### 核心需求

1. 目标存在且启用时，点击触发传入的处理函数；初始目标为 `null` 不报错。
2. 目标由旧元素变成新元素后，旧元素不再触发处理函数，新元素正常工作。
3. 禁用时停止监听，重新启用后恢复；反复切换不会重复注册。
4. 返回一个永久停止本次监听的操作。它可以重复调用；停止后，即使目标或启用状态变化也不再恢复。
5. 组件卸载时自动释放本次调用创建的资源，不要求每个组件额外编写相同的清理代码。
6. 调用方的处理函数应收到 `MouseEvent`，不要求调用方使用 `any` 或类型断言。

### 设计约束

- 在组件 `setup` 阶段同步调用；不要求支持任意时间或任意作用域外的调用。
- 目标和启用状态发生变化后，最迟在本轮 Vue 更新处理完成后满足新的监听关系。
- 不使用轮询、全局 DOM 查询或第三方 composable 库。
- 两次调用即使监听同一元素，也必须能独立停止。调用方为两次调用提供不同的处理函数。
- 本题不要求实现所有 DOM 事件的通用类型映射。

### 思考问题

1. 普通值、ref、computed 和 getter 在本题中分别意味着“一次性输入”还是“持续变化的输入”？
2. 你会如何在 `MaybeRef`、`MaybeRefOrGetter` 或自定义类型之间选择？如果使用 `toValue`，读取发生的位置会影响什么？
3. 目标与启用状态共同决定监听关系，你如何在 `watch`、`watchEffect` 和其他方式中做取舍？
4. 目标替换、临时禁用、永久停止和组件卸载，各自意味着哪些资源需要结束？如何判断清理已经完整？
5. 如果以后需要在组件以外的 effect scope 中使用，`onUnmounted`、`onScopeDispose` 或其他清理契约应如何取舍？本题的 API 是否需要随之调整？

### 验收场景

- 初始目标为 `null`，挂载后点击面板一次，计数变为 `1`。
- 将目标从元素 A 切到元素 B，等待本轮更新完成：点击 A 不计数，点击 B 只增加一次。
- 将启用状态改为 `false` 后等待更新，点击不计数；恢复为 `true` 后点击一次只增加一次。
- 连续禁用、启用三次，再点击一次，计数只增加一次。
- 调用永久停止操作两次，再替换目标并重新启用，点击仍不计数。
- 卸载组件后，对之前保留的元素引用派发点击事件，不再调用处理函数。
- 同一元素上创建两次监听，停止第一份后，第二份仍正常接收点击。

## 第 4 题：搜索、筛选与分页组合 `useUserList`

### 题目背景

后台一次性拿到用户列表后，需要在浏览器中完成关键词搜索、状态筛选和分页。当前组件里散落着多份列表与页码处理逻辑，经常出现“筛选后停在空白页”的问题。

请设计业务 composable `useUserList`，并将其中能独立复用的分页规则提取为 `usePagination`。

### 已有代码 / 初始条件

```ts
interface User {
  id: number
  name: string
  email: string
  status: 'active' | 'disabled'
}

type StatusFilter = 'all' | User['status']

export function usePagination(/* TODO：自行设计参数 */) {
  // TODO
}

export function useUserList(/* TODO：接收用户数据源 */) {
  // TODO：组合业务筛选与分页能力。
}
```

用户数据源支持普通数组、ref、computed 或 getter。响应式数据源只要求支持整份数组替换，不要求侦听用户对象内部的原地修改。

初始关键词为空，状态为 `all`，页码为 `1`，每页 `10` 条。验收数据共 `23` 人，ID 为 `1` 至 `23`，按 ID 升序排列；姓名为 `用户1` 至 `用户23`，邮箱为 `user1@example.com` 至 `user23@example.com`；ID `1` 至 `13` 为 `active`，其余为 `disabled`。

### 核心需求

1. 对姓名和邮箱进行不区分大小写的子串匹配；关键词两端的空格不参与匹配。状态条件与关键词条件同时生效，结果保持原始顺序。
2. 对外提供关键词、状态、当前页、每页条数、筛选后总数、总页数、当前页用户，以及上一页和下一页是否可用。
3. 关键词或状态发生有效变化时回到第 `1` 页；规范化后的关键词没有变化时，保留当前页。
4. 每页条数仅支持 `5`、`10`、`20`，发生变化时回到第 `1` 页；设置相同条数不改变页码。
5. 数据源替换后，如果当前页仍有效则保留；如果越界，则移动到新的最后一页。
6. 没有结果时，总数为 `0`、总页数为 `0`、当前页仍为 `1`、当前页用户为空，翻页操作无效果。
7. 翻页仅接受正整数页码；非法页码忽略，超出总页数的正整数定位到最后一页。提供重置操作，一次恢复所有初始查询条件和分页设置。

### 设计约束

- `useUserList` 必须实际使用 `usePagination`；后者不认识 `User`、关键词或用户状态。
- 不修改传入的数组或用户对象，不请求接口，不加入缓存或防抖。
- 公开 API 必须明确哪些字段可以直接编辑、哪些只能读取、哪些需要操作函数修改。
- 不为每一个简单表达式都创建单独的 composable；自行说明保留在业务层的职责。
- 所有关联状态最迟在本轮 Vue 更新处理完成后保持一致；不要求同步读取每个中间步骤。

### 思考问题

1. 原始列表、筛选后列表、当前页列表和各种数量之间，哪些应该独立保存？哪些重复保存会产生同步问题？
2. “搜索条件变化回第一页”和“数据减少后修正页码”分别由谁负责？如何避免两个 composable 相互驱动、循环修改？
3. 为什么简单地把所有变化都解释成“回第一页”不能满足本题？你的依赖关系如何体现这些差异？
4. 分页的输入需要持续读取筛选结果总数，你会设计怎样的参数契约？调用方传一个当前数字快照会发生什么？
5. 如果某段逻辑目前只用一次，你如何判断提取 composable 的价值，而不是只看代码行数？

### 验收场景

- 初始共 `23` 条、`3` 页；跳到第 `3` 页，显示 ID `21`、`22`、`23`。
- 在第 `3` 页选择 `active`，回到第 `1` 页，总数为 `13`、总页数为 `2`。
- 在上述筛选下跳到第 `2` 页，替换数据源并删掉 ID `1`：仍停在第 `2` 页，总数变为 `12`。
- 独立重置到原始 `23` 条数据，跳到第 `3` 页后，将数据源替换成仅包含 ID `1` 至 `12` 的数组：移动到第 `2` 页，显示 ID `11`、`12`。
- 恢复原始数据和初始设置，搜索 ` USER2@ `，仅匹配 ID `2`；搜索不存在的姓名，得到约定的空结果状态。
- 搜索 `user`，跳到第 `2` 页，再把关键词改成 ` USER `，页码仍为 `2`。
- 当前每页 `10` 条且位于第 `2` 页，设置每页 `10` 条后页码不变；改成 `5` 条后回第 `1` 页。
- 修改关键词、状态和分页后执行重置，恢复初始设置，并根据当前数据源展示结果。
- 页面同时创建两个 `useUserList`，操作其中一个不会改变另一个的查询条件与分页。

## 第 5 题：处理参数变化与乱序返回的 `useRequest`

### 题目背景

用户详情抽屉根据选中的用户 ID 加载资料。用户快速切换列表行时，后发请求可能先返回，旧请求也可能在新请求成功后失败。请设计一个可复用的异步请求 composable，让抽屉始终展示当前选择对应的请求状态。

### 已有代码 / 初始条件

```ts
interface UserDetail {
  id: number
  name: string
}

interface ProductDetail {
  id: number
  title: string
}

// 这些是已有服务的类型声明，不是待实现的 composable。
declare function fetchUser(id: number): Promise<UserDetail>
declare function fetchProduct(id: number): Promise<ProductDetail>

export function useRequest<T, P>(/* TODO：设计服务、参数源及选项 */) {
  // TODO
}
```

先以用户 ID 为参数完成接入，再用商品服务验证复用性。参数源至少能接收普通数字、ref、computed 和 `() => props.userId`。本题只验收数字参数，不要求实现对象参数的深比较。

服务层由调用方提供，可以通过可手动控制完成顺序的 Promise 模拟成功或失败，无需真实后端。服务不保证提供取消能力。

### 核心需求

1. 对外暴露 `data`、`loading`、`error`、`refresh()`、`cancel()`。设计它们的类型，并明确操作函数的返回契约。
2. 初始 `data` 为 `undefined`，`error` 为 `null`；默认立即请求，也支持关闭首次自动请求。
3. 首次自动请求关闭时，初始不请求，但之后参数的有效值变化仍自动请求。没有变化的值不重复触发自动请求；`refresh()` 总是使用调用时的最新参数发起请求。
4. 新请求开始时清空旧 `data` 与 `error`，令 `loading` 为 `true`。当前有效请求成功时写入结果；失败时保持 `data` 为 `undefined`，并提供可展示的 `Error`。
5. 任意时刻，只有最后一次发起且未失效的请求有资格更新公开状态。旧请求成功、失败或结束，都不能影响新请求的结果、错误和加载状态。
6. `cancel()` 立即令当前请求失效，将 `loading` 设为 `false`，保留调用这一刻已有的 `data` 和 `error`；重复取消无副作用。取消不阻止后续参数变化或手动刷新发起新请求。
7. 组件卸载后释放本次调用创建的资源，未完成请求后续的成功或失败不再改变状态，也不能产生未处理的 Promise rejection。
8. 调用方直接从用户服务获得 `UserDetail | undefined`，从商品服务获得 `ProductDetail | undefined`，无需断言响应类型；错误输入按 `unknown` 处理。

### 设计约束

- 在组件 `setup` 阶段同步调用；本题仅要求组件生命周期内使用。
- `data`、`loading`、`error` 由 composable 管理，调用方不能直接赋值来改变请求状态。
- 两次独立调用的请求状态互不影响。
- 即使底层请求无法真正中断，也必须满足取消和竞态要求。
- 请求服务函数在一次 composable 调用的生命周期内不变；参数有效值变化后，最迟在本轮 Vue 更新处理完成后发起新请求。
- 不加入缓存、重试、请求合并、LRU、RxJS 或通用状态机。无需沿用第 4 题的本地分页规则。

### 思考问题

1. 请求参数与异步结果分别由谁拥有？普通数字与 getter 作为输入时，你承诺的响应行为有何不同？
2. 如果 A、B 两个请求都在处理中，A 先结束时直接将 `loading` 改为 `false`，界面可能出现什么现象？
3. “底层网络操作结束”和“这个结果仍允许更新界面”是否是一回事？服务无法中断时，取消应该承诺什么？

### 验收场景

- 默认模式传入普通数字 `1`：首次发起一次请求，成功后展示用户 `1`；关闭首次自动请求时，初始保持空闲，调用 `refresh()` 后才请求。
- 关闭首次自动请求并传入 ID ref：将 ID 从 `1` 改为 `2` 后自动请求；再次设置为 `2` 不新增请求。
- 分别传入 ref、computed 和 props getter，上游有效 ID 改变后均请求新 ID；其中一次调用不会改变其他调用的状态。
- 按下面的顺序手动控制请求完成，最终结果始终是 B 的用户，且没有旧错误覆盖：

  ```text
  ID = 1，发出 A
  ID 改为 2，发出 B
  B 先成功，显示用户 2，loading 为 false
  A 后成功，仍显示用户 2
  ```

- 重复上述流程，让 A 最后失败：B 的结果保留，`error` 仍为 `null`，没有未处理的 rejection。
- A 尚未完成时发出 B，让 A 先结束、B 仍等待：`loading` 仍为 `true`，`data` 仍为 `undefined`，`error` 仍为 `null`。
- 同一 ID 连续刷新两次，第二次刷新先成功，第一次刷新稍后成功或失败，都不能覆盖第二次刷新状态。
- 当前有效请求失败：`loading` 为 `false`，`data` 为 `undefined`，错误可展示；随后刷新成功，错误被清除。
- 请求中调用 `cancel()`：立即结束加载；旧请求稍后完成不写入状态。再次刷新可正常得到结果。
- 已有成功数据且没有请求进行时调用 `cancel()`，保留成功数据。请求中取消两次，也不抛出异常。
- 请求未完成时卸载组件，再让请求成功或失败：保留用于检查的返回状态不再变化，没有未处理的 rejection；重新挂载时使用全新的请求状态。
